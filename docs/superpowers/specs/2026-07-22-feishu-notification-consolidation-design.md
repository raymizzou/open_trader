# 飞书通知收敛设计

## 目标

把飞书从多个后台流程各自发声的状态流，收敛成可快速判断和处理的通知入口：

- 保留趋势日报、控制器异常、订单异常、保护线触发和回撤阻断；
- 合并跨市场 OpenD 故障；
- 合并同市场、同方向、同状态的订单提醒；
- 停止把普通监控状态、旧盘前流程和非关键 watcher 状态发送到飞书；
- 保留现有检测、事件账本、Dashboard 展示、macOS 和小爱音箱行为。

本设计只改变飞书路由、去重与文本展示，不改变策略判断、订单提交、保护线计算、行情检查或 Dashboard 数据。

## 当前问题

当前仅配置了一个飞书通道 `feishu_app`，消息过多并非 webhook 与应用通道重复，而是多个生产者独立发送：

- 三个趋势市场控制器分别发送报告、阻塞、订单和复盘通知；
- 共享 OpenD 故障会被 CN、HK、US 分别报告；
- 完整错误字符串参与去重，错误文本变化会产生新通知；
- watcher 按标的发送保护线缺失、价格未知、执行截止和连接状态；
- 旧盘前流程保留开始、阻塞、行动、完成四类通知；
- 手工 watcher 仍可发送交易计划和做 T 通知。

飞书配置继续使用纯文本格式，不引入卡片协议、消息编辑、队列服务或新依赖。

## OpenD 故障合并

### 故障分类

OpenD 相关错误先归一化为稳定类别，完整错误文本不再直接充当跨市场去重键：

1. `connectivity`：不可达、连接超时、断线、协议断开和等价的连接失败；
2. `rate_limit`：行情、订单、历史订单等 OpenD 请求限频。

连接故障和限频故障的处理方式不同，因此分别发送。相同类别在 CN、HK、US 之间合并成一条。非 OpenD 控制器异常不进入共享事件，继续按市场和稳定异常类型发送。

### 共享事件状态

复用现有 JSON、原子替换和 `RunLock`，不增加服务：

- 锁：`data/trend_controller/shared/opend-incidents.lock`
- 连接事件：`data/trend_controller/shared/incidents/opend-connectivity.json`
- 限频事件：`data/trend_controller/shared/incidents/opend-rate-limit.json`

每个事件状态至少包含：schema 版本、故障类别、是否活动、首次发现时间、最近更新时间、受影响市场、各市场最近原因、飞书送达时间和成功渠道。

三个 controller 在写共享事件前获取同一把锁：

1. 第一个发现故障的 controller 把事件标记为活动并发送一条飞书；
2. 后续 controller 只补充受影响市场和原因，不重复发送；
3. 正常 OpenD 检查会清除对应市场的降级状态；
4. 所有已降级市场均恢复后，把事件标记为已恢复，但不发送恢复通知；
5. 下一次新故障可以再次发送。

第一条消息直接说明 CN、HK、US 均可能受影响，因此无需等待三个 controller 都报告失败才发送。

### 共享状态失败

共享账本使用原子替换，避免部分写入。如果账本不可读、锁失败或状态无法更新，则退回现有按市场发送的 A3 通知，并保留原错误。回退的最坏结果是临时多一条消息，不允许静默丢失控制器故障。

## 订单通知分组

订单通知的分组键固定为：

```text
交易日 + 市场 + 买卖方向 + 状态
```

其中：

- 市场为 CN、HK 或 US；
- 方向为买入或卖出，从冻结报告和动作账本取得；
- 状态包括未完成、失败、不确定、冲突、错过窗口、部分成交、已提交、受阻等当前业务状态；
- 不同方向或不同状态绝不合并；
- 同组多个标的在一条消息中逐项列出并去重。

如果 C2 属于批次或基础设施失败且无法绑定具体动作方向，则明确发送“批次执行失败”，不猜测买入或卖出。动作账本损坏导致方向无法读取时同样进入 C2，而不是产生方向未知的订单提醒。

### 截止提醒

到达市场截止时间时，先读取所有动作目录的最新不可变事件，再分组发送 C1。组消息发送成功后，为组内每个标的追加现有 `trend_review_deadline_notified` 送达事实，并记录同一个组标识。发送失败时不写任何组内送达事实，下一轮重试整个组。

### 状态变化

同一标的从一种异常状态进入另一种异常状态时可以发送新状态。例如“部分成交”与后续“错过窗口”是两个不同判断。相同分组状态不重复发送。

## 文本格式

继续发送纯文本，使用三种固定标题层级：

```text
【日报｜券商｜市场趋势报告｜日期】
【需处理｜来源｜问题类型｜日期】
【紧急｜券商｜市场保护线触发｜标的】
```

正文固定按以下顺序组织：

1. 发生了什么；
2. 影响什么；
3. 现在做什么；
4. 标的明细或简短技术原因。

### OpenD 连接故障

```text
【需处理｜系统｜OpenD 连接故障｜2026-07-22】

影响：CN、HK、US 行情与订单监控可能中断
首次发现：2026-07-22 18:42
现在做：启动或检查 OpenD 登录与网络状态
原因：连接超时
```

### 分组订单提醒

```text
【需处理｜老虎｜美股买入未完成｜2026-07-22】

状态：错过买入窗口
现在做：今日不再追单

标的：
- HIG
- HST
```

### 保护线触发

```text
【紧急｜老虎｜美股保护线触发｜HIG】

最新价：133.90
活动保护线：134.1650
现在做：人工确认并全部卖出
```

A1 日报主体继续使用现有买卖清单，不扩大审计内容。A2–A7、B1 和 C1–C3 不展示内部英文枚举、堆栈、完整本地路径、密钥或认证信息。必要的技术原因保留为最后一行的简短中文描述。D7 文本保持不变。

## 实现边界

采用定点修改，不建设中央事件总线：

- 复用 `send_notification_with_results` 的渠道过滤；
- 在 B2–B6、D1–D6 的现有发送点关闭飞书渠道；
- 在趋势控制器通知路径增加 OpenD 错误归类和共享事件账本；
- 在订单截止与控制器订单通知路径增加一个纯分组函数和一个纯文本渲染函数；
- 继续使用现有日报冻结账本、watch event JSONL 和 controller notification JSON；
- 不改变 notifier 配置格式，不新增环境变量；
- 不改变 macOS、小爱音箱、Dashboard 或策略执行接口。

现有直接调用 `notifier.notify` 的 D5、D6 路径改用已有的带渠道过滤发送函数，以便只排除飞书而不影响其他配置渠道。B2、B3 当前只有飞书输出，停止发送后只保留事件记录。B4、B5 继续路由到 macOS 和小爱。B6 只记录语音失败事件。

## 发送失败与重试

- 飞书发送失败不得写入已送达状态；
- OpenD 共享事件在飞书成功后才记录送达时间和渠道；
- 分组订单通知在整组成功后才写组内每个标的的送达事实；
- A1、A2 继续重试冻结标题与正文，不以新内容替换已冻结消息；
- B1 继续保持现有按渠道独立送达和重放规则；
- 被关闭的飞书类型不以摘要、恢复消息或其他标题绕过路由矩阵。

## 测试

自动测试必须覆盖：

1. A1–A7、B1、C1–C3、D7 可以进入飞书路径；
2. B2–B6、D1–D6 不进入飞书路径，但对应事件和非飞书渠道保持；
3. 三个并发 controller 报告同类 OpenD 连接故障时只产生一次飞书送达；
4. OpenD 连接与限频分别发送，完整错误文本变化不造成同类重复；
5. 共享事件恢复后再次故障可以重新发送；
6. 共享账本或锁失败时回退按市场通知；
7. 订单按市场、方向和状态分组，同组标的去重；
8. 买入与卖出、不同异常状态互不合并；
9. 分组发送失败不写部分送达事实，重试仍包含整组；
10. A1/A2 继续按券商分开发送和冻结；
11. B1 继续按标的和交易日去重；
12. D7 继续发送原始测试标题和正文。

## 现场验证与部署

此变更影响飞书、后台 controller、launchd 和长期运行进程，单元测试不足以证明上线行为。

完成实现后必须：

1. 运行相关通知、watcher、controller、日报和订单分组测试并记录精确结果；
2. 运行完整 pytest，确认无回归；
3. 用受控并发场景直接运行三个 controller 通知路径，确认共享 OpenD 事件只有一个成功发送记录；
4. 通过 D7 执行一次真实飞书测试，确认 `feishu_app` 成功；
5. 检查三个现有 launchd controller，停止仍运行旧代码的进程；
6. 部署同一 Git SHA 并重启 CN、HK、US controller；
7. 核对新 PID、工作目录、Git SHA、启动时间和新日志；
8. 观察至少一个正常 controller 轮询周期，确认没有 B2–B6 或 D1–D6 飞书发送尝试。

本任务不修改 Dashboard 行为或页面；在没有 Dashboard 源码或数据变更的前提下，不把 `make acceptance` 作为该通知任务的完成门槛。

## 验收标准

- 用户每天继续分别收到东方财富、辉立和老虎趋势日报；
- 同一持续 OpenD 连接故障在 CN、HK、US 之间只收到一条飞书；
- OpenD 限频与连接故障保持不同通知；
- 订单通知明确区分市场、买卖方向和状态，同组多个标的只占一条；
- 保护线触发仍按标的即时发送；
- C 系列和 D7 保持可用；
- B2–B6、D1–D6 不再产生飞书消息；
- 被关闭的通知仍能在原事件账本或 Dashboard 中审计；
- 三个 controller 运行新代码且日志没有新增通知路由错误。
