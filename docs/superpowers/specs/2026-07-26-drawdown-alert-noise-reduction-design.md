# 回撤预检通知降噪设计

## 目标

减少部署过程产生的无效飞书噪声，同时保留回撤风险控制的失败关闭行为：

- 部署前验收失败只阻止部署并保留日志，不通知用户；
- 真正需要处理的回撤预检失败按一次运行合并成一条中文通知；
- 通知直接说明发生了什么、影响什么和现在做什么；
- 不改变回撤计算、状态继承、交易限制或 Dashboard 数据。

## 问题与根因

`make acceptance` 使用真实配置运行 `trend-drawdown-preflight`，并传入
`actor=acceptance`。预检失败时仍会构建真实 notifier，因此尚未通过验收的
中间代码会把每个市场的内部英文异常分别发送到飞书。

2026-07-25 的 CN v9、HK v6 和 US v6 告警就是一次部署前验收失败。失败的
中间版本没有通过门禁或完成部署；修复后的 SHA 随后通过验收并成功建立三个
市场的回撤状态。

当前通知还存在两个展示问题：

- 按市场逐条发送，同一根因会产生三条消息；
- 直接展示内部英文异常，没有影响范围和处置动作。

## 方案

### 验收阶段静默

CLI 根据已有的 `actor` 选择 notifier：

- `actor=acceptance` 使用 `NullNotifier`；
- 其他 actor 继续使用配置中的真实 notifier。

验收静默只关闭外部通知。预检仍读取真实数据、写入合法的回撤状态、返回原有
退出码，并在失败时阻止后续部署；静默 notifier 也不会更新通知送达账本。

不新增命令参数、环境变量或配置项。

### 生产故障合并

`_sync_failure_alerts` 保留现有活动键：

```text
市场 | 策略版本 | 故障类型
```

一次预检先收集本轮尚未通知的失败，再发送一条合并消息。发送成功后一次性把
对应活动键写入账本；发送失败则不写入，下一次自然运行继续重试。

恢复成功仍按市场和版本清除活动键，因此后续再次出现同类故障时可以重新通知。
同一运行中不同市场或不同故障类型都放在一条消息里逐项列出。

### 文案

标题固定为：

```text
【需处理｜系统｜累计回撤状态阻断】
```

正文格式为：

```text
发生：累计回撤状态未通过部署预检
影响：CN v9、HK v6、US v6 暂停新开仓；卖出和保护线继续运行
现在做：让 Codex 检查回撤预检并重新部署；不要手动解除限制

明细：
- CN v9：历史基线不可用
- HK v6：历史基线不可用
- US v6：历史基线不可用
```

通知只展示稳定的中文故障分类，不展示内部英文枚举、异常堆栈或本地路径。已知
故障类型使用简短中文描述；未知类型统一显示“回撤预检失败”，完整错误继续保留
在命令输出和日志中。

## 安全与失败语义

- 所有回撤预检失败仍然失败关闭并阻止新开仓；
- 卖出和保护线流程不依赖新开仓资格，继续运行；
- 通知发送失败不改变预检结果，也不会解除限制；
- 验收静默不创建或清除通知送达账本；
- 不因通知合并而合并或丢失活动键；
- 不发送“恢复成功”通知。

## 不做

- 不增加延迟、计时器、重试队列或“最终失败”状态；
- 不建设中央通知服务或新的 notifier 抽象；
- 不改飞书卡片协议、配置格式或 Dashboard；
- 不修改回撤基线选择和跨版本继承逻辑。

## 测试与验证

自动测试覆盖：

1. `actor=acceptance` 的 CLI 运行不调用真实 notifier，失败仍返回原退出码；
2. 非 acceptance actor 继续构建真实 notifier；
3. 三个市场同轮失败只发送一条消息；
4. 消息包含发生、影响、现在做和中文明细，不含内部英文错误；
5. 发送成功后按原活动键去重，恢复后再次失败可以重新通知；
6. 发送失败不写活动键，也不改变失败关闭结果。

实现完成后运行相关测试、完整 pytest 和使用记录 notifier 的直接预检工作流。
该任务不修改 Dashboard，因此不运行 `make acceptance`。同时确认没有常驻进程
缓存 `trend-drawdown-preflight` 代码；该命令若只由验收流程按次启动，则无需
重启后台服务。
