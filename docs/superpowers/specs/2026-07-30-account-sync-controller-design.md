# 唯一账户与行情同步控制器设计

## 背景

当前 Dashboard 在 `/api/quotes` 请求中调用账户同步服务。同步函数先覆盖
`data/latest/portfolio.csv`，随后用“旧文件中的其他券商行必须继续存在”
进行校验；校验失败再恢复旧文件。

这条链路有三个问题：

1. Dashboard 从展示层变成了数据生产者，浏览器轮询会触发账户写入。
2. 保护规则无法区分真实数据丢失和已归零、已消失的旧仓位，可能把正确
   的新快照判成失败并恢复旧组合。
3. Dashboard 从 `portfolio.csv` 读取持仓，同时从最新运行目录读取账户
   明细和汇总。未发布或失败的候选明细也可能被选中，造成汇总与持仓
   来自不同批次。

本次事故中，老虎新快照包含 14 个美股持仓，但旧组合只包含 8 个。
保护逻辑恢复旧组合后，Dashboard 又读取了新运行目录中的老虎汇总，
最终同时显示“14 个持仓”的汇总和 8 行真实持仓。

## 目标

- 账户与 Dashboard 行情只有一个外部读取入口和一个发布入口。
- Dashboard 成为纯文件投影，不连接券商、不触发同步、不写账户文件。
- 同步结果先生成候选并校验，成功后发布；失败时不存在“先写后回滚”。
- 每个券商独立更新。一个来源失败时，其他成功来源仍可发布。
- 失败、过期和未知状态必须在 Dashboard 明确显示，不能被旧数据伪装成
  正常。
- 账户汇总、现金、持仓和来源状态来自同一份已接受快照。
- 依赖过期账户数据的新做T提醒和策略动作失败关闭。

## 非目标

- 不把下单、撤单和成交核验改造成统一券商网关。
- 不增加数据库、消息队列或事件溯源系统。
- 不增加 Dashboard 或 CLI 的“立即同步”通道。
- 不重新设计整个 Dashboard；只移除刷新入口并展示真实状态。
- 不改变交易控制器下单前直接查询券商交易 API 的安全核验能力。

## 唯一所有权

新增一个由 `launchd` 托管的账户与行情同步控制器。它是以下 Dashboard
数据链路的唯一外部读取者和唯一发布者：

```text
富途账户 / 富途行情 / 老虎账户
                |
                v
      账户与行情同步控制器
                |
                v
          已接受文件快照
                |
                v
       Dashboard 文件投影
```

所有权规则：

- 同步控制器读取富途账户、富途行情和老虎账户 API。
- 同步控制器独占写入本设计定义的 `data/latest` 账户、组合、行情和状态
  文件。
- Dashboard 后端只读取这些文件；浏览器轮询只重新读取文件投影，不触发
  外部同步。
- 盘前任务不再调用 `refresh_live_portfolio()` 覆盖 `latest`，而是校验
  控制器快照的鲜度后读取已发布组合。
- 月结单导入只生成已校验来源文件，不能直接更新组合 `latest`。同步控制器
  接受来源后统一重建组合。
- 现有富途、老虎 live check/sync 生产命令必须移除，或改为只读取控制器
  已发布状态；控制器运行时不存在第二条直连券商的诊断或同步入口。
- 交易控制器可以在下单前直接查询账户、订单和成交事实，但不能发布本设计
  的 Dashboard 账户或行情文件。

## 进程模型

控制器是一个长期运行进程：

- 行情周期：5 秒。
- 富途账户周期：60 秒。
- 老虎账户周期：60 秒。
- 各周期独立记录成功和失败；行情失败不能修改账户状态，账户失败也不能把
  行情标成失败。
- 启动后立即执行首次同步，不等待第一个完整周期。

`launchd` 负责启动和自动重启。控制器在整个生命周期持有
`data/account_sync/controller.lock` 的独占进程锁。第二个实例无法获得锁时
立即退出并记录“已有同步控制器运行”。该锁只负责保证唯一进程，不用于协调
多个写入者。

## 已发布文件

同步控制器独占写入：

```text
data/latest/account_sync_state.json
data/latest/portfolio.csv
data/latest/quotes.json
data/account_sync/controller_status.json
```

### `account_sync_state.json`

这是 Dashboard 账户页面的唯一事实源。它保存每个券商最后成功的账户明细
以及当前同步状态：

```json
{
  "version": 1,
  "generation": "2026-07-30T12:10:00+08:00",
  "brokers": {
    "tiger": {
      "status": "failed",
      "attempted_at": "2026-07-30T12:10:00+08:00",
      "last_success_at": "2026-07-30T11:56:54+08:00",
      "data_as_of": "2026-07-30T11:56:54+08:00",
      "message": "账户同步失败",
      "positions": [
        {
          "market": "US",
          "symbol": "DRAM",
          "quantity": "100"
        }
      ],
      "cash": [
        {
          "currency": "USD",
          "cash_balance": "1000"
        }
      ],
      "summary": {
        "position_count": 1,
        "cash_count": 1
      }
    }
  }
}
```

示例中的 `positions`、`cash` 和完整 `summary` 实际保留最后成功内容；同步
失败只修改状态字段，不清空已接受数据。错误信息必须清洗，不包含账户号、
凭据、私钥、令牌或本机敏感路径。

持久状态只使用 `ok`、`failed` 和 `unknown`：

- `ok`：最近一次尝试成功。
- `failed`：最近一次尝试失败，已接受数据保持不变。
- `unknown`：没有可信状态记录。

`stale` 是读取时派生状态：`ok` 的最后成功时间超过三个同步周期后，API 和
Dashboard 将其显示为 `stale`。`skipped` 只表示调度器本轮无需执行，永远
不能覆盖券商状态。

### `portfolio.csv`

这是兼容现有策略流程的组合投影。它只由下列已接受来源确定性重建：

- 富途最后成功账户快照；
- 老虎最后成功账户快照；
- 辉立和东方财富最后接受的月结单来源。

它不再是 Dashboard 账户汇总和真实持仓的来源。Dashboard 账户页面只使用
`account_sync_state.json`，避免组合聚合行与券商明细再次错批。

### `quotes.json`

保存当前报价、报价来源状态、抓取时间和最后成功时间。格式复用现有
Dashboard 报价字段，Dashboard 的 `/api/quotes` 只读取该文件。

行情最后成功时间超过 15 秒时显示为过期。市场休市时仍记录一次成功读取的
休市状态，不能仅因价格不变而判过期。

### `controller_status.json`

保存：

- PID；
- 启动时间；
- 当前工作目录；
- Git SHA；
- 最近心跳；
- 最近账户循环和行情循环结果；
- 当前阻塞原因。

最后心跳超过 15 秒时，Dashboard 将控制器显示为不可用。

## 候选、校验和发布

每个实时券商按以下步骤独立运行：

```text
获取完整快照
  -> 规范化为候选账户状态
  -> 校验该券商完整性
  -> 与其他已接受来源重建候选组合
  -> 校验组合
  -> 发布组合
  -> 发布新的账户状态
```

校验通过前不修改任何 `data/latest` 文件。成功时先原子替换完整
`portfolio.csv`，再原子替换 `account_sync_state.json`。Dashboard 不读取
`portfolio.csv` 作为账户事实，因此进程在两次替换之间退出时最多暂时保留
旧账户页面，不会把新旧批次混成“正常”。控制器重启后的首次循环会重新确定
性发布。

失败时：

- `portfolio.csv` 不变；
- 该券商最后成功的 `positions`、`cash` 和 `summary` 不变；
- 只把该券商状态更新为 `failed`，记录尝试时间、最后成功时间和清洗后的
  原因；
- 继续处理其他来源；
- 全局状态显示异常。

不存在恢复旧文件的“回滚”分支。旧数据之所以继续可见，是因为失败候选从未
获得发布资格。

行情使用独立的原子 `quotes.json` 发布，不参与账户组合事务。

## 完整性规则

券商候选只有在以下条件全部满足时才能发布：

- 账户列表查询完整；
- 持仓分页完整；
- 资产和现金查询成功；
- 必需标识与数值字段可解析；
- 同一账户、市场、标的和币种没有重复记录；
- 券商明细与账户汇总能够对账；
- 所有已接受来源可以确定性重建组合。

明确允许：

- 持仓数量减少；
- 旧标的从完整新快照中消失；
- 完整快照返回零持仓；
- 已归零仓位被删除。

控制器按券商替换自己的已接受快照，因此不再需要“其他券商旧行必须继续
存在”的启发式保护。未更新券商的数据由状态结构天然保留。

候选运行和失败诊断可以继续写入 `data/runs/...` 与报告目录，但这些文件
不能被 Dashboard 或下一次组合发布按“最新目录”自动选中。

## 月结单来源

辉立和东方财富导入流程只生成规范化、已校验的来源候选及导入报告。同步
控制器检测到新的有效来源后，将它接受到自己的状态中并重建组合。

月结单状态始终显示为非实时，并展示账期。缺失或格式失败的必需月结单来源
显示异常，但不能覆盖上一次已接受来源。

## Dashboard 行为

移除“刷新账户与行情”按钮及所有账户同步副作用：

- Dashboard 不构造 `DashboardAccountSyncService`。
- `/api/quotes` 不调用账户同步，也不连接富途，只读取 `quotes.json`。
- `/api/dashboard` 从 `account_sync_state.json` 构造账户卡片、真实持仓、
  现金和券商汇总。
- Dashboard 不再扫描 `data/runs/.../extracted_positions.csv`、
  `extracted_cash.csv` 或账户快照来猜测最新账户状态。

顶层只显示二元结果：

- `同步正常`：控制器心跳正常，所有必需实时来源在各自时效内，最近组合
  发布成功。
- `同步异常`：控制器停止、来源失败、来源过期、来源未知或部分来源失败。

异常明细按券商展示：

- `同步失败 · 数据截至 11:56`
- `数据已过期 · 数据截至 11:56`
- `同步状态未知 · 数据未验证`

失败和过期时继续展示最后成功持仓，但整个券商区域明确标记异常。行情状态
与账户状态独立；行情正常不能掩盖账户同步失败。

## 动作安全

盘前流程读取 `account_sync_state.json` 并要求相关账户状态为当前。失败、
过期或未知时，不生成依赖当前持仓的新动作。

`watch-t` 是直接从组合持仓生成新做T信号和提醒的入口。它必须读取账户同步
状态：

- 涉及 `failed`、`stale` 或 `unknown` 券商的仓位不生成新提醒；
- 已有历史信号可以继续展示，但状态改为“人工复核”；
- 纯行情和技术数据采集可以继续运行，但不能改变账户状态或绕过账户门禁。

交易控制器的下单前账户、订单和成交核验保持独立，并继续以实时券商交易
事实失败关闭。

## 启动与迁移

首次部署时：

1. 停止旧 Dashboard，确保旧进程不能继续触发账户同步。
2. 部署同一 Git SHA 的同步控制器和只读 Dashboard。
3. 启动同步控制器；没有状态文件时先写 `unknown`。
4. 等待富途、老虎和行情首次真实成功循环。
5. 由控制器接受现有有效月结单来源并发布首个完整组合。
6. 启动只读 Dashboard。

首次成功前，Dashboard 必须显示“同步异常 / 数据未验证”，不能根据旧
`portfolio.csv` 推断为正常。

现有 `check-futu-account`、`check-tiger-account`、
`sync-futu-portfolio`、`sync-tiger-portfolio` 的生产直连入口必须移除或
改为读取控制器文件；月结单 `--update-latest` 与盘前直接刷新组合的生产
路径必须移除或改为只生成候选，避免保留隐藏读写入口。

## 测试与验收

自动化测试至少覆盖：

- Dashboard 不再创建同步服务、连接券商或显示刷新按钮。
- `/api/dashboard` 和 `/api/quotes` 只投影已发布文件。
- 控制器成功发布账户、组合、行情和状态。
- 富途失败、老虎成功时，老虎更新，富途保留最后成功快照并标失败，全局
  显示异常。
- 完整快照删除旧仓位时正常发布，不触发保护恢复。
- 失败候选写入运行目录后，Dashboard 仍只显示已接受快照。
- 状态跨控制器和 Dashboard 重启保留；超过三个周期后变为过期。
- 第二个控制器实例无法启动。
- `watch-t` 对失败、过期和未知账户状态失败关闭。
- 月结单、手动同步和盘前流程不能直接更新 `latest`。

直接工作流验证必须使用真实富途、老虎和行情连接，并检查：

- 唯一控制器 PID、工作目录、Git SHA 和新鲜心跳；
- 首次成功及一次受控失败后的状态文件；
- 失败后最后成功持仓仍可见且明确标红；
- Dashboard 进程没有券商连接和账户文件写入；
- Dashboard 桌面与移动端显示一致；
- 评审 URL 返回 HTTP 200。

完成实现后，按项目规则只在最终候选 SHA 上运行一次 `make acceptance`。
只有结果为 `PASS`，并重新部署完全相同的已验收 SHA，才能交付用户评审。
