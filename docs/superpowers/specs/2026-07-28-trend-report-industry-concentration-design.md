# Trend Report Right-Side Structure Design

**Date:** 2026-07-28
**Status:** Approved in conversation
**Markets:** CN, US, HK

## Goal

Extend the existing `行业上下文` table so each eligible industry's right-side
trend shows both:

- the share of constituents on the right side; and
- the share of industry market value represented by those constituents.

Both metrics show the latest earlier valid trading-day value followed by the
current value. Explanations are available by hovering, focusing, or clicking
the metric text.

This is report context only. It does not add an industry cap or change candidate
filtering, ordering, target weights, stop-loss rules, or risk budgets.

## Confirmed Design

1. Reuse the existing `行业上下文` section, table, typography, spacing, colors,
   desktop layout, and mobile card layout.
2. Rename the displayed `右侧占比` column to `右侧个数占比`.
3. Add one adjacent `右侧市值占比` column.
4. Do not add a card, chart, summary strip, or separate `变化` column.
5. Each available metric cell displays `前值 → 当前值`.
6. Metric text is the explanation trigger; no separate information icon is
   required.
7. Tooltip copy is generated by deterministic rules, never by an LLM.
8. Missing optional aggregate data remains explanatory only and never invalidates
   the industry's existing trading context.
9. Existing reports are immutable; no historical backfill is required.

## Data Sources

The existing local industry-member calculation remains unchanged and continues
to provide:

- `right_count`, `valid_count`, and `right_share`;
- coverage validation;
- the historical breadth key used by current candidate ordering; and
- audit evidence.

For the displayed pair, request these Trend Animals aggregate fields for each
eligible industry `tmId` in the existing industry-state snapshot request:

- `TrendRightSideCountRatio`;
- `TrendRightSideMktCapRatio`.

The two displayed ratios therefore come from the same provider row, industry,
denominator universe, and `asOfDate`. The report must not combine the locally
calculated count ratio with the provider market-cap ratio in the paired display
or structure explanation.

Each aggregate ratio is optional and valid only when it is finite, between zero
and one inclusive, and belongs to the expected report data date. Invalid or
wrong-date values become unavailable without changing the existing
`IndustryContext.valid` result.

The report's API audit and cost total include both requested fields using the
billing catalog returned for that run.

## Report Data

Add four optional facts to each frozen `IndustryContext`:

- `aggregate_right_count_ratio`;
- `aggregate_right_market_cap_ratio`;
- `prior_aggregate_right_count_ratio`;
- `prior_aggregate_right_market_cap_ratio`.

The current facts come from the same-date industry-state row. The prior facts
come from the latest valid stored industry context whose date is earlier than
the current report date.

The existing industry-context history gains the two current aggregate ratios.
Its reader remains backward-compatible with legacy history rows that do not
contain them. Such rows provide the existing temperature/local-breadth history
but no aggregate prior value.

No extra exposure model, storage system, or background job is added.

## Derived Values

Renderers derive, rather than store, the following exact values:

```text
count change pp = (current count ratio - prior count ratio) × 100
market-cap change pp = (current market-cap ratio - prior market-cap ratio) × 100
structure gap pp = (current market-cap ratio - current count ratio) × 100
prior structure gap pp = (prior market-cap ratio - prior count ratio) × 100
structure-gap change pp = structure gap pp - prior structure gap pp
```

The structure gap has no strategy threshold. It describes whether right-side
participation is weighted toward larger or smaller constituents; it does not
represent account exposure or an estimated probability of further gains.

## Presentation

The existing table becomes:

```text
行业 | 当前温度 | 温度方向 | 趋势强度 | 温转热数量 |
右侧个数占比 | 右侧市值占比
```

Example:

```text
银行 | 热 | 上升 | 100 | 6 | 15.0% → 19.1% | 60.0% → 65.0%
```

There is no `变化` column because both metric cells already express change.

Display states:

- current and prior available: `15.0% → 19.1%`;
- current available, prior unavailable: `19.1% · 基准建立中`;
- current unavailable: `未提供`.

The existing local numerator/denominator remains in the audit payload and keeps
its current strategy role, but is not substituted into either aggregate display
cell.

### Tooltip interaction

The column label and each available metric value use a text-style button with
the existing report font and a subtle dashed underline:

- pointer users can hover;
- touch users can tap to open and tap elsewhere to close;
- keyboard users can focus, open, and dismiss with Escape.

The tooltip may overlay the table but must not introduce a new report card or
change row height.

The count tooltip states its denominator and exact prior-day change.

The market-cap tooltip states:

1. its denominator;
2. its exact prior-day change;
3. the exact current structure gap;
4. the exact structure-gap change when both prior ratios exist; and
5. `该指标不是账户仓位或上涨概率`.

Example deterministic copy:

> 右侧市值占比 65.0%，较前一有效交易日上升 5.0 个百分点。
> 当前高于右侧个数占比 19.1% 共 45.9 个百分点，右侧更偏大市值成分；
> 结构差较前值扩大 0.9 个百分点。该指标不是账户仓位或上涨概率。

Unavailable facts are omitted from the sentence rather than guessed. The
Dashboard and Markdown renderers use the same formulas and wording rules.

## Scope Boundaries

This change does not add:

- an industry position-count or account-weight cap;
- per-industry account exposure or risk-attribution rows;
- a new candidate score, filter, ordering key, or position-sizing rule;
- a breadth threshold or breadth-based market gate;
- an LLM call, charting dependency, database, notification, or backfill job;
- changes to the existing 0.4% single-entry, 4% portfolio, or 1% abnormal-loss
  risk controls.

The existing `组合计划风险` section remains the authority for the planned
stop-loss budget.

## Error Handling

- If one aggregate field is unavailable, show `未提供` only for that field.
- Calculate the structure gap only when both current aggregate fields are valid.
- Calculate changes only when the corresponding current and prior values are
  valid.
- A first valid aggregate observation establishes the baseline; it does not
  trigger a historical API fetch.
- Legacy frozen reports and history remain readable and render with their
  existing fields.
- Optional aggregate failures do not change report actions or candidate order.

## Verification

Focused tests cover:

1. extraction and validation of both aggregate fields from the same-date
   industry-state row;
2. current, prior, first-baseline, missing, invalid, and wrong-date states;
3. the three derived changes and signed structure gap;
4. backward-compatible legacy history and frozen-report reading;
5. JSON and Markdown output;
6. the existing Dashboard table with exactly the two ratio columns and no
   `变化` column;
7. hover, click, keyboard, desktop, and mobile behavior; and
8. identical candidate ordering and actions with and without the optional
   aggregate fields.

Development uses focused tests and direct report checks. Because this changes
Dashboard behavior, `make acceptance` is the final review gate. Only `PASS` is
review-ready; the exact accepted Git SHA is then redeployed and verified before
the review URL is shared.

## Rollout

The change applies only to newly generated reports. It is additive and does not
require a strategy-version change because no trading decision changes.
